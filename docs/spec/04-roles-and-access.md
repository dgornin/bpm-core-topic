# 4. Роли, права доступа и участники процесса (A4–A7, A11, A14, A15, команда `matrix`)

Раздел описывает, **кто и что может делать с документами**: роли (групповые и
привязанные к записи), матрицу прав `access`, неявные права из входов переходов,
команду `matrix` и проверки участников процесса — видят ли исполнители и роли
переходов свой документ, не теряет ли участник доступ на полпути, можно ли
заполнить обязательные поля, создать документ и выполнить разделение обязанностей.

Все коды раздела относятся к **уровню B** (см. `tests/levels.json`).
Реализация — модуль `bpmcore/access.py` (функции `effective_cells` и
`check_access`); значения по умолчанию для ролей и прав подставляет нормализация
(`bpmcore/normalize.py`).

Примеры: `examples/demo_topic.json` (согласование темы), `examples/leave_request.json`
(заявка на отпуск). Кейсы раздела — каталоги `tests/cases/acc-*`.

В примерах ниже показаны только изменённые фрагменты; остальное — как в
`examples/demo_topic.json`: модель `topic` с полями `x_name` (обязательное) и
`x_description`; роли `author` (привязка `create_uid`), `head` и `student`
(групповые); процесс `topic` с узлами `draft` (старт, исполнитель `author`) →
`review` (исполнитель `head`) → `published` / `rejected`; переходы `submit`
(`author`, требует `x_description`), `approve`, `rework` (возврат в `draft`),
`reject` (все три — `head`); `sod: [["submit", "approve"]]`.

---

## 4.1. Группы и роли

### Группа

Группа (`groups[]`) — набор пользователей платформы. Для этого раздела важен
только её ключ `key`: роли ссылаются на группы по ключу. Остальные поля групп —
в `01-ir-format.md`.

### Роль

Роль (`roles[]`) — то, через что конфигурация раздаёт права и назначает
исполнителей.

| Поле | Тип | Обязательно | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | строка-ключ | да | — | ключ роли |
| `name` | строка | да | — | название |
| `groups` | непустой список ключей групп | да | — | у кого вообще может быть роль: только у членов этих групп. Нормализация убирает повторы и сортирует список |
| `see_all` | булево | нет | `false` | роль видит все записи во всех узлах (см. ниже) |
| `bindings` | объект `{ключ модели: путь}` | нет | `{}` | привязка роли к записям моделей |

В тестах `see_all` встречается только как `true`, `false` или отсутствует
(= `false`); поведение при небулевых значениях не проверяется.

### Виды ролей

* **Групповая роль** — `bindings` пуст (`{}` или ключа нет). Роль есть у
  каждого члена любой из её групп, на **всех** записях. Пример: `head`
  (заведующий), `student`.
* **Роль по записи** (роль с привязкой) — `bindings` не пуст. Для модели `M` из
  `bindings` пользователь имеет роль на конкретной записи `M`, только если он
  находится по пути `bindings[M]` от этой записи. Примеры:
  `{"topic": "create_uid"}` — автор записи; `{"request": "x_manager_id"}` —
  пользователь из поля «руководитель»; `{"topic": "x_project_id.user_id"}` —
  руководитель проекта, на который ссылается тема.
  Роль по записи может иметь права `read`, `write`, `unlink` только на те модели,
  к которым она привязана (см. 4.2, `S1.access`); право `create` — на любую.
* **Роль с `see_all`** — флаг «видит всё»: права такой роли действуют на все
  записи модели и во всех узлах процесса. Формально см. предикат `can` в 4.4.
  `see_all` можно задать и групповой роли, и роли с привязкой.

**Единственный держатель.** Если последнее поле пути привязки роли `r` к модели
`M` имеет тип `many2one`, на каждой записи `M` роль `r` есть не больше чем у
одного пользователя. Если последнее поле — `many2many`, держателей может быть
несколько. Это различие использует `A11.sod_unsatisfiable`.

### Путь привязки

Путь — строка из имён полей через точку: `"create_uid"`, `"x_manager_id"`,
`"x_project_id.user_id"`. Путь разбирается от модели `M` (ключа из `bindings`):

1. Текущая модель — `M`. Для каждого сегмента по порядку: сегмент должен быть
   полем текущей модели. Поля модели приложения — её поля из `fields` (после
   нормализации: с автоматически добавленным `x_name`) **плюс служебные поля**,
   которые есть у любой записи:

   | Служебное поле | Тип | Связь |
   |---|---|---|
   | `id` | `integer` | — |
   | `create_uid` | `many2one` | `res.users` |
   | `write_uid` | `many2one` | `res.users` |
   | `create_date` | `datetime` | — |
   | `write_date` | `datetime` | — |

   Поля внешней модели (`res.users`, `project.project`, ...) берутся из снимка
   платформы (`spec/snapshot.json`, раздел `external_models.<модель>.fields`)
   плюс те же служебные поля.
2. Каждый сегмент, кроме последнего, должен быть связью (`many2one`,
   `one2many`, `many2many`); следующий сегмент ищется в модели, на которую
   ссылается связь (`relation`: модель приложения — по ключу или техническому
   имени, внешняя — по имени из снимка).
3. Последнее поле должно иметь тип `many2one` или `many2many` и `relation`,
   равный `"res.users"`.
4. Ни один сегмент не может быть `write_uid`: «последний правивший» — это
   любой, кто нажал кнопку, и роль переходила бы к нему.

Нарушение любого пункта — ошибка нормализации `S1.binding` (сводка в 4.2).

## 4.2. Матрица прав `access`

Раздел `access` — список строк прав (ячеек). Одна строка:

| Поле | Тип | Обязательно | Смысл |
|---|---|---|---|
| `role` | ключ роли | да | кому |
| `model` | ключ модели приложения | да | на какую модель. Только ключ модели из `models` (не техническое имя `x_...` и не внешняя модель) |
| `op` | `"read"` \| `"write"` \| `"create"` \| `"unlink"` | да | операция: читать, изменять, создавать, удалять |
| `nodes` | непустой список ключей узлов | нет | в каких узлах процесса модели действует право |
| `fields` | список имён полей | нет | для `write` — какие поля можно менять, для `create` — какие поля можно заполнить при создании. У `read` и `unlink` поле игнорируется |

Операции независимы: `write` не даёт `read`, `create` не даёт `write` и т.д.

### Нормализация строки прав (значения по умолчанию)

Пусть `M` — модель строки, `P` — процесс, привязанный к `M` (если есть).

* **`nodes` не задан:**
  * у `M` есть процесс и `op` ≠ `create` → все узлы процесса `P`;
  * у `M` нет процесса или `op` = `create` → узлов нет. Такое право действует
    «вне узлов»; в матрице и в формулах ниже оно обозначается узлом `"*"`.
* **`nodes` задан** (допустим только у моделей с процессом и только при
  `op` ≠ `create`) → повторы убираются; порядок значения не имеет.
* **`fields` при `op` ∈ {`write`, `create`}:** не задан → все поля модели из
  `fields` (включая автоматически добавленный `x_name`, без служебных полей);
  задан → повторы убираются, список сортируется. Пустой список `[]` допустим:
  право есть, но ни одного поля.

Пример: в демо строка `{"role": "author", "model": "topic", "op": "read"}`
превращается в право `read` в узлах `draft`, `review`, `published`, `rejected`,
а `{"role": "author", "model": "topic", "op": "create"}` — в право `create` в
узле `"*"` с полями `["x_description", "x_name"]`.

### Ошибки нормализации ролей и прав (сводка)

Полное описание кодов `S1.*` и порядка нормализации — в `02-schema-checks.md`;
здесь — только то, что касается ролей и прав. Все эти коды — уровня B,
находка `error`. Если нормализация дала хоть одну ошибку, проверки этого
раздела (4.6–4.7) **не выполняются**, а `matrix` отвечает находками (4.5).

| Код | Условие | `where` |
|---|---|---|
| `S1.role_groups` | `groups` роли отсутствует или пуст, либо среди его элементов есть ключ несуществующей группы (ожидается непустой список ключей групп) | `{role}` |
| `S1.binding` | `bindings` — не объект | `{role}` |
| `S1.binding` | ключ в `bindings` — не ключ модели приложения (техническое имя, внешняя модель, неизвестный ключ) | `{role}` |
| `S1.binding` | путь не разбирается (не строка, пустой, нет такого поля, промежуточное поле не связь), содержит `write_uid` или не заканчивается полем `many2one`/`many2many` на `res.users` | `{role, model}` |
| `S1.access` | `role` строки — не ключ роли | `{cell}` |
| `S1.access` | `model` строки — не ключ модели приложения | `{role, cell}` |
| `S1.access` | `op` не из четырёх допустимых | `{role, cell}` |
| `S1.access` | `nodes` задан у модели без процесса | `{role, cell}` |
| `S1.access` | `nodes` задан, но это не непустой список строк — ключей узлов процесса модели | `{role, cell}` |
| `S1.access` | `nodes` задан при `op` = `create` (создание бывает только до старта процесса) | `{role, cell}` |
| `S1.access` | `op` ∈ {`write`, `create`} и `fields` не список или содержит имя, которого нет в `fields` модели (служебные поля тоже нельзя) | `{role, cell}` |
| `S1.access` | у роли непустой `bindings`, модели строки в нём нет и `op` ≠ `create` (непонятно, к каким записям относится право) | `{role, model}` |

`cell` — номер строки в `access`, с нуля. После первых трёх ошибок строка
дальше не проверяется; остальные условия проверяются независимо (одна строка
может дать несколько `S1.access`).

Кейсы: `acc-s1-access-unbound-model`, `acc-s1-access-create-nodes`,
`acc-matrix-not-normalized` (`S1.access`); `acc-s1-binding-not-users`,
`acc-s1-binding-write-uid` (`S1.binding`).

## 4.3. Неявные права из входов переходов (`inputs`)

У перехода может быть список `inputs` — поля, которые нажимающий заполняет в
момент перехода (например, заведующий вводит резолюцию, утверждая тему). Это
даёт ролям перехода право на запись этих полей в исходном узле. Правило:

> Для каждого процесса `P` с моделью `M`, каждого перехода `t` с непустым
> `inputs` и каждой роли `r` из `t.by` добавляется **неявная ячейка**
> `{role: r, model: M, op: "write", nodes: [t.from], fields: t.inputs}`.

* Переход с пустым `by` (например, системный) неявных прав не даёт.
* Неявные ячейки не проходят проверки `S1.access` (в том числе проверку
  привязки роли к модели): они строятся уже после нормализации.
* Корректность самих `inputs` (поля модели процесса, не служебные, не
  `one2many`/`many2many`; иначе `S1.field_ref`) проверяет нормализация.

**Эффективные права** (`E`) — нормализованные строки `access` плюс все неявные
ячейки. Именно они используются в команде `matrix` и во всех проверках ниже.

Пример: переход `{"key": "approve", "from": "review", "by": ["head"], "inputs": ["x_resolution"]}`
даёт ячейку `head / topic / write / review / ["x_resolution"]`.

## 4.4. Предикаты над эффективными правами

Для ячейки `c ∈ E` обозначим `nodes(c)` — её список узлов, или `{"*"}`, если
узлов нет (модель без процесса или `create`).

* **Узлы права:** `Ops(r, M, op)` — объединение `nodes(c)` по всем `c ∈ E` с
  `c.role = r`, `c.model = M`, `c.op = op`. Пустое множество — права нет вовсе.
* **Может (с учётом `see_all`):**
  `can(r, M, op, n)` истинно, если
  (`r.see_all` и `Ops(r, M, op) ≠ ∅`) **или** `"*" ∈ Ops(r, M, op)` **или**
  `n ∈ Ops(r, M, op)`.
  То есть роль с `see_all`, у которой есть **хотя бы одна** ячейка
  `(r, M, op)`, может `op` на `M` в любом узле.
* **Поля записи:** `W(r, M, n)` — объединение `c.fields` по всем `c ∈ E` с
  `c.role = r`, `c.model = M`, `c.op = "write"` и `n ∈ nodes(c)` или
  `"*" ∈ nodes(c)`. **`see_all` здесь не учитывается.**
* **Кто-нибудь пишет поле:** `writable_by_anyone(M, f)` — существует
  `c ∈ E` с `c.model = M`, `c.op = "write"`, `f ∈ c.fields` (любая роль, любой
  узел). Права `create` не считаются.

## 4.5. Команда `matrix`

```text
<impl> matrix IR.json [--snapshot SNAP.json]
```

Команда показывает итоговые права конфигурации. Алгоритм:

1. Прочитать IR. Не читается / не JSON → `{"error": "..."}`, код выхода 4.
2. Нормализовать IR (коды `S1.*`). Если есть хотя бы одна ошибка — вывести
   **тот же JSON, что и `validate`** на этом IR (`{"verdict": "reject",
   "findings": [...]}` с находками нормализации), код выхода 1.
3. Иначе построить `E` (4.3). Для каждой `c ∈ E` и каждого узла
   `n ∈ nodes(c)` (`"*"`, если узлов нет) взять ключ
   `(c.role, c.model, c.op, n)`; ячейки с одинаковым ключом слить в одну,
   для `write` и `create` объединив `fields`.
4. Вывести `{"cells": [...]}`, код выхода 0. Каждая ячейка —
   `{"role", "model", "op", "node"}` и для `write`/`create` ещё `"fields"` —
   отсортированный список (может быть пустым); у `read` и `unlink` ключа
   `fields` нет. Ячейки отсортированы по `(role, model, op, node)` обычным
   сравнением строк (по кодам символов; `"*"` меньше любой буквы).

Что **не** делает `matrix`:

* не выполняет анализ: ошибки структуры, участников, эффектов, политики на
  вывод не влияют (конфигурацию, которую `validate` отклоняет из-за `A14`,
  `matrix` всё равно показывает, код 0);
* не раскрывает `see_all`: выводятся только узлы из строк прав;
* не выводит права, следующие из других прав (`write` не добавляет `read`).

`model` в ячейке — ключ модели; `node` — ключ узла или `"*"`. Опция
`--policy` у `matrix` не поддерживается.

**Пример** — `examples/demo_topic.json` (все 11 ячеек):

```json
{"cells": [
  {"role": "author", "model": "topic", "op": "create", "node": "*", "fields": ["x_description", "x_name"]},
  {"role": "author", "model": "topic", "op": "read", "node": "draft"},
  {"role": "author", "model": "topic", "op": "read", "node": "published"},
  {"role": "author", "model": "topic", "op": "read", "node": "rejected"},
  {"role": "author", "model": "topic", "op": "read", "node": "review"},
  {"role": "author", "model": "topic", "op": "unlink", "node": "draft"},
  {"role": "author", "model": "topic", "op": "write", "node": "draft", "fields": ["x_description", "x_name"]},
  {"role": "head", "model": "topic", "op": "read", "node": "published"},
  {"role": "head", "model": "topic", "op": "read", "node": "rejected"},
  {"role": "head", "model": "topic", "op": "read", "node": "review"},
  {"role": "student", "model": "topic", "op": "read", "node": "published"}
]}
```

**Пример слияния.** Если к демо добавить поля `x_resolution`, `x_note` и

```json
"flows": [..., {"key": "approve", ..., "by": ["head"], "inputs": ["x_resolution"]},
               {"key": "reject", ..., "by": ["head"], "inputs": ["x_note", "x_resolution"]}],
"access": [..., {"role": "head", "model": "topic", "op": "write", "nodes": ["review"], "fields": ["x_note"]},
                {"role": "head", "model": "topic", "op": "write", "nodes": ["review"], "fields": []}]
```

то четыре ячейки `head / topic / write / review` (две неявные, две явные)
сливаются в одну: `{"role": "head", "model": "topic", "op": "write", "node": "review", "fields": ["x_note", "x_resolution"]}`.

Тесты сравнивают множество ячеек точно (включая `fields`); повторяющиеся
ячейки — ошибка.

Кейсы: `acc-matrix-demo`, `acc-matrix-leave-request` (узел-развилка — тоже узел
прав), `acc-matrix-inputs` (неявные права и слияние), `acc-matrix-trip`
(справочник без процесса → узел `"*"`, `see_all` не раскрывается, `x_name`
добавлен нормализацией), `acc-matrix-ignores-analysis`,
`acc-matrix-not-normalized` (код 1), `acc-matrix-not-json` (код 4).

## 4.6. Проверки участников и прав: когда и в каком порядке

1. Проверки выполняются **только если нормализация прошла без ошибок**
   (иначе в ответе только `S1.*`).
2. Для каждого процесса `P` из `processes` (модель `M = P.model`) выполняются
   проверки 4.7.1–4.7.7: исполнители шагов, роли переходов, непрерывность,
   обязательные поля, разделение обязанностей. `A6.no_trigger` выдаётся тем же
   обходом выходов узлов, что и структура процесса (`03-structure.md`, шаг 4).
3. Затем по всей конфигурации: создание документов (4.7.8–4.7.9), обязательные
   поля при создании (4.7.10), видимость связанных записей (4.7.11).
4. Проверки не зависят друг от друга и от находок структуры (недостижимые узлы,
   тупики и т.п. проверки прав не отключают), **кроме двух исключений**: если
   в процессе не ровно один стартовый узел (`S3.start` без `node`), то для этого
   процесса **не выдаются** `A6.no_trigger` и `A7.creator_read`.
5. Порядок находок в ответе не важен. Одна и та же ошибка в нескольких местах
   даёт находку на каждое место.

Две проверки зависят от понятий уровня A (`05-conditions-effects-policy.md`):
системные переходы (`system: true`) не дают `A6.no_trigger`, а поле,
записываемое действием `set`, не проверяется в `A5.requires`. В кейсах уровня B
ни системных переходов, ни действий нет.

## 4.7. Коды по одному

### 4.7.1. A14.assignee_read — исполнитель шага не видит документ

* **Уровень:** B. **Находка:** error. **Где:** `{process, node}`.
* **Условие:** у узла `n` задан исполнитель `a = n.assignee` (исполнитель бывает
  только у шагов) и **не** `can(a, M, "read", n)`.
* **Почему ошибка:** документ «назначен» человеку, который его не видит в этом
  узле — работа встанет.
* **Пример:**

  ```json
  {"role": "head", "model": "topic", "op": "read", "nodes": ["published", "rejected"]}
  ```

  (заведующий — исполнитель `review`) → `A14.assignee_read`,
  `where = {"process": "topic", "node": "review"}`. Заодно `A6.by_read` для
  `approve`, `rework`, `reject` — их роль тоже не видит документ в `review`.
* **Детали:** роль с `see_all`, у которой есть хоть одна строка `read` на `M`,
  видит документ во всех узлах — `A14` для неё не бывает.
* **Кейсы:** `acc-a14-assignee-read`; зелёный — `acc-see-all-accept`.

### 4.7.2. A6.assignee_no_action — исполнитель не может выполнить ни один переход

* **Уровень:** B. **Находка:** warning. **Где:** `{process, node}`.
* **Условие:** у узла `n` задан исполнитель `a`, и `a` не входит в `by` ни
  одного выхода `n` (переходов с `from = n`). Узел без выходов тоже даёт
  находку (вместе с `S3.dead_end`).
* **Почему предупреждение:** шаг повиснет на человеке, который не может его
  завершить, — но, возможно, это задумано (переход нажмёт кто-то другой).
* **Пример:** `{"key": "review", "name": "На утверждении", "assignee": "author"}`
  → `A6.assignee_no_action`, `where = {"process": "topic", "node": "review"}`
  (вердикт `accept`: автор видит тему, но `approve`, `rework`, `reject` доступны
  только `head`).
* **Кейсы:** `acc-a6-assignee-no-action`.

### 4.7.3. A6.by_read — роль перехода не видит документ

* **Уровень:** B. **Находка:** error. **Где:** `{process, flow}`.
* **Условие:** для перехода `t` (любого: из шага, развилки или конечного узла)
  и роли `r ∈ t.by`: **не** `can(r, M, "read", t.from)`. Одна находка на пару
  (переход, роль).
* **Почему ошибка:** у роли есть кнопка перехода, но документ в этом узле она
  не видит и нажать её не сможет.
* **Пример:** `{"key": "rework", ..., "from": "review", "by": ["head", "student"]}`
  (студент читает тему только в `published`) → `A6.by_read`,
  `where = {"process": "topic", "flow": "rework"}`.
* **Кейсы:** `acc-a6-by-read`, `acc-a14-assignee-read`.

### 4.7.4. A6.no_trigger — переход некому выполнить

* **Уровень:** B. **Находка:** error. **Где:** `{process, flow}`.
* **Условие:** в процессе ровно один стартовый узел, переход `t` выходит из
  **шага** (`type = step`), `t.auto` ложно, `t.by` пуст и `t.system` ложно.
* **Не проверяются:** выходы развилок (для них `S3.xor_*`), выходы конечных
  узлов (`S3.end_out`), автоматические переходы из шагов (вместо этого
  `S3.auto`), системные переходы, а также все переходы процесса, если стартовых
  узлов не ровно один.
* **Почему ошибка:** переход не нажмёт ни один человек и не вызовет движок —
  ветка процесса мертва.
* **Пример:** `{"key": "approve", "from": "review", "to": "published", "by": []}`
  → `A6.no_trigger`, `where = {"process": "topic", "flow": "approve"}`.
* **Кейсы:** `acc-a6-no-trigger`.

### 4.7.5. A4.continuity — участник теряет доступ после перехода

* **Уровень:** B. **Находка:** error. **Где:** `{process, role, node}`, где
  `node` — узел, **в котором** доступ потерян.
* **Какие роли проверяются:** роль `r` с `r.see_all = false`, у которой в
  `bindings` есть модель процесса `M` (роль по записи этого документа).
  Групповые роли, роли с `see_all` и роли, привязанные только к другим
  моделям, не проверяются.
* **Условие:** пусть `R = Ops(r, M, "read")`. Если `R` пуст или содержит
  `"*"` — роль не проверяется (`"*"` у модели с процессом получается, только
  если в процессе нет ни одного узла: тогда раскрытие `nodes` по умолчанию
  даёт пустой список, а ячейка без узлов действует на все записи). Иначе для каждого узла `n ∈ R` и **каждого** перехода `t` с
  `t.from = n` (любого вида, включая возвраты и автоматические): если
  `t.to ∉ R` и `r ∉ release(t.to)` — ошибка. Одна находка на такой переход.
* `release` — список ключей ролей у узла (по умолчанию `[]`): узел явно
  «отпускает» эти роли — терять в нём доступ для них нормально.
* **Важно — только один шаг:** проверяются только переходы **из** узлов, где
  роль видит документ. Если роль видит документ только в `draft`, а `review`
  её отпускает, то узлы после `review` уже не проверяются (участник выведен из
  процесса).
* **Почему ошибка:** участник (автор, руководитель по полю) вдруг перестаёт
  видеть свой документ: права были написаны для прошлого узла и забыты для
  следующего. Если так задумано — нужно указать роль в `release`.
* **Пример:**

  ```json
  {"role": "author", "model": "topic", "op": "read", "nodes": ["draft"]}
  ```

  → `A4.continuity`, `where = {"process": "topic", "role": "author", "node": "review"}`.
  Добавив `"release": ["author"]` узлу `review`, получим `accept`.
* **Кейсы:** `acc-a4-continuity`, `acc-a4-continuity-return` (потеря доступа
  при возврате `rework` в `draft`); зелёные — `acc-a4-release-accept`,
  `acc-a4-group-role-accept`, `acc-a4-see-all-accept`, `acc-trip-accept`
  (руководителя отпускает узел оформления).

### 4.7.6. A5.requires и A5.requires_source — обязательные поля перехода

`requires` перехода — поля, которые должны быть заполнены, чтобы переход можно
было выполнить. Для перехода `t` процесса `P` (модель `M`) и каждого поля
`f ∈ t.requires`:

1. Если `f ∈ t.inputs` (поле вводится в момент перехода) — поле не
   проверяется.
2. Если `f` записывается действием `set` любого перехода любого процесса в
   модель `M` (уровень A, см. `05-conditions-effects-policy.md`) — поле не
   проверяется.
3. Иначе, если **не** `writable_by_anyone(M, f)` — ошибка **`A5.requires`**.
4. Иначе, если нет роли `r ∈ t.by` с `f ∈ W(r, M, t.from)` — предупреждение
   **`A5.requires_source`** (при пустом `by` — тоже).

Обе находки: `where = {process, flow}`.

#### A5.requires

* **Уровень:** B. **Находка:** error.
* **Условие:** шаг 3: никакая роль ни в каком узле не может записать поле
  (с учётом неявных прав из `inputs` других переходов). Право `create`
  не считается: поле можно задать при создании, но если его потом очистили или
  не заполнили — заполнить его уже некому.
* **Пример:** `{"role": "author", "model": "topic", "op": "write", "nodes": ["draft"], "fields": ["x_name"]}`
  (а `submit` требует `x_description`) → `A5.requires`,
  `where = {"process": "topic", "flow": "submit"}`.
* **Кейсы:** `acc-a5-requires`; зелёный — `acc-a5-inputs-accept` (то же, но
  `submit` сам вводит `x_description` через `inputs`).

#### A5.requires_source

* **Уровень:** B. **Находка:** warning.
* **Условие:** шаг 4: поле кто-то пишет, но ни одна роль перехода не может
  записать его в исходном узле перехода. `see_all` здесь не помогает
  (используется `W`).
* **Почему предупреждение:** поле должно быть заполнено раньше, кем-то другим;
  если не заполнили — переход встанет.
* **Пример:** `{"key": "approve", "from": "review", "by": ["head"], "requires": ["x_description"]}`
  (поле пишет только автор в `draft`) → `A5.requires_source`,
  `where = {"process": "topic", "flow": "approve"}`, вердикт `accept`.
* **Кейсы:** `acc-a5-requires-source`, `acc-a5-requires-source-implied`
  (поле пишут только через `inputs` другого перехода).

### 4.7.7. A11.sod_unsatisfiable — разделение обязанностей невыполнимо

* **Уровень:** B. **Находка:** error. **Где:** `{process}`.
* **Условие:** для пары `[t1, t2]` из `P.sod` (разделение обязанностей: два
  перехода должен выполнить не один и тот же человек): `set(t1.by) = set(t2.by)`,
  в этом множестве ровно одна роль `r`, у `r` есть привязка к модели процесса
  (`bindings[M]`), и последнее поле этого пути — `many2one` (единственный
  держатель, 4.1).
* **Не ошибка:** роли переходов различаются или их больше одной; роль
  групповая (людей в группе может быть несколько); привязка через `many2many`.
* **Почему ошибка:** оба перехода может нажать только один человек на этом
  документе, а SoD запрещает ему нажать второй — процесс застрянет.
* **Пример:** `{"key": "approve", ..., "by": ["author"]}` при
  `sod: [["submit", "approve"]]` (`author` — `create_uid`) → `A11.sod_unsatisfiable`,
  `where = {"process": "topic"}`.
* **Кейсы:** `acc-a11-sod-unsatisfiable`, `acc-a11-sod-path` (привязка
  `x_project_id.user_id`); зелёные — `acc-a11-many2many-accept`,
  `acc-a11-group-role-accept`.

### 4.7.8. A7.no_creator — документ никто не может создать

* **Уровень:** B. **Находка:** warning. **Где:** `{process}`.
* **Условие:** для процесса `P` нет ни одной роли `r` с `Ops(r, M, "create") ≠ ∅`.
* **Почему предупреждение:** документ можно создать только действиями других
  процессов — возможно, так и задумано.
* **Пример:** из `access` удалена строка `{"role": "author", "model": "topic", "op": "create"}`
  → `A7.no_creator`, `where = {"process": "topic"}`, вердикт `accept`.
* **Кейсы:** `acc-a7-no-creator`.

### 4.7.9. A7.creator_read — создатель не видит созданное

* **Уровень:** B. **Находка:** error. **Где:** `{process, role}`.
* **Условие:** в процессе ровно один стартовый узел `s`; для каждой роли `r` с
  `Ops(r, M, "create") ≠ ∅`: **не** `can(r, M, "read", s)`.
* **Почему ошибка:** созданный документ сразу оказывается в стартовом узле, и
  создатель его там не видит.
* **Пример:** `{"role": "student", "model": "topic", "op": "create"}` (студент
  читает только `published`) → `A7.creator_read`,
  `where = {"process": "topic", "role": "student"}`.
* **Кейсы:** `acc-a7-creator-read`; зелёный — `acc-a4-see-all-accept`
  (создатель с `see_all` и `read` только в `published`).

### 4.7.10. A7.required_not_creatable — создатель не может заполнить обязательное поле

* **Уровень:** B. **Находка:** error. **Где:** `{role, model}`.
* **Условие:** для каждой строки `c` раздела `access` с `op = "create"` (модель
  `M` — любая, с процессом или без) вычисляется список `missing` — поля `f`
  модели `M` (из `fields` после нормализации, включая `x_name`), такие что:
  1. `f.required` истинно;
  2. тип `f` — один из `char`, `text`, `html`, `date`, `datetime`, `selection`,
     `many2one` (у `integer`, `float`, `boolean`, `one2many`, `many2many` есть
     естественное пустое значение — они не проверяются);
  3. у `f` нет ключа `default`;
  4. `f ∉ c.fields`;
  5. роль `c.role` не является **заполнителем ссылки на родителя** для `f`
     (см. ниже).

  Если `missing` не пуст — ошибка. Одна находка на строку `create`.
* **Заполнитель ссылки на родителя.** Пусть в какой-то модели `Q` есть поле
  `o` типа `one2many` со связью на `M` и `o.inverse = f` (строки списка `o`
  ссылаются на родителя через `f`). Роль `r` — заполнитель для `f`, если в
  `access` есть строка роли `r` на модель `Q` с `op` ∈ {`create`, `write`} и
  `o ∈ fields` этой строки (после нормализации). Тогда `r` добавляет записи `M`
  из списка родителя, и ссылку `f` заполняет платформа.
* **Почему ошибка:** сервер требует обязательные поля при создании, а заполнить
  их создатель не вправе — создать запись невозможно.
* **Пример:** `{"role": "author", "model": "topic", "op": "create", "fields": ["x_description"]}`
  → `A7.required_not_creatable`, `where = {"role": "author", "model": "topic"}`
  (обязательное `x_name` не входит в поля создания).
* **Кейсы:** `acc-a7-required-not-creatable`, `acc-a7-required-inverse`;
  зелёные — `acc-a7-required-exempt-accept` (обязательные `integer` и
  `selection` со значением по умолчанию), `acc-a7-required-inverse-accept`
  (автор может писать список этапов темы).

### 4.7.11. A15.related_read — связанная запись невидима

* **Уровень:** B. **Находка:** warning. **Где:** `{role, model}`, где `model` —
  ключ модели, **из которой** идёт ссылка.
* **Условие:** для каждой модели приложения `M`, каждого её поля `f` типа
  `many2one`, ссылающегося на **модель приложения** `T` (ссылки на внешние
  модели не проверяются), и каждой роли `r`:
  `Ops(r, M, "read") ≠ ∅` и **не** `sees_any(r, T)`. Одна находка на
  каждую тройку (модель `M`, поле `f`, роль `r`). `where` у находок для
  разных полей одной модели совпадает, поэтому имя поля стоит указать в
  `message`.
* **`sees_any(r, T)`** истинно, если `Ops(r, T, "read") ≠ ∅`, **или**
  для **каждой** группы `g` из `r.groups` найдётся роль `o` (любая), у которой
  `g ∈ o.groups`, (`o.see_all` или `o.bindings` пуст) и `Ops(o, T, "read") ≠ ∅`.
  Смысл: члены группы получают права всех её групповых ролей, так что роль по
  записи, которой нельзя читать справочник напрямую, может видеть его через
  групповую роль своей группы.
* **Почему предупреждение:** роль видит документ, но ссылка в нём ведёт в
  запись, которую роль никогда не увидит (пустое поле или ошибка доступа в
  интерфейсе).
* **Пример:**

  ```json
  "models": [..., {"key": "category", "name": "Направление", "kind": "reference"}],
  "fields": [..., {"name": "x_category_id", "type": "many2one", "label": "Направление", "relation": "category"}]
  ```

  и никто не читает `category` → `A15.related_read` для `author`, `head`,
  `student` с `model = "topic"`. Если добавить групповую роль
  `{"key": "staff", "groups": ["teacher", "head"]}` с правом `read` на `category`,
  останется только находка для `student`.
* **Кейсы:** `acc-a15-related-read`; зелёные — `acc-a15-group-cover-accept`,
  `acc-trip-accept`.

## 4.8. Псевдокод

```
effective_cells(ir):
    E = [нормализованные строки ir.access]
    for P in ir.processes:
        for t in P.flows:
            if t.inputs:
                for r in t.by:
                    E.append({role: r, model: P.model, op: write, nodes: [t.from], fields: t.inputs})
    return E

check_access(ir, E):
    for P in ir.processes:
        M = P.model; starts = [n in P.nodes if n.start]
        for n in P.nodes with n.assignee = a:
            if not can(a, M, read, n): error A14.assignee_read {process, node: n}
            if a not in ∪{t.by : t.from = n}: warning A6.assignee_no_action {process, node: n}
        for t in P.flows, r in t.by:
            if not can(r, M, read, t.from): error A6.by_read {process, flow: t}
        if |starts| == 1:
            for t in P.flows with node(t.from).type == step and not t.auto and not t.by and not t.system:
                error A6.no_trigger {process, flow: t}
        for r in roles with not r.see_all and M in r.bindings:
            R = Ops(r, M, read)
            if R is empty or "*" in R: continue
            for n in R, t in P.flows with t.from = n:
                if t.to not in R and r not in node(t.to).release:
                    error A4.continuity {process, role: r, node: t.to}
        for t in P.flows, f in t.requires:
            if f in t.inputs or f in SET_FIELDS(M): continue   # SET_FIELDS(M) — поля M, которые пишет set (п. 2 в 4.7.6)
            if not writable_by_anyone(M, f): error A5.requires {process, flow: t}
            elif no r in t.by with f in W(r, M, t.from): warning A5.requires_source {process, flow: t}
        for [t1, t2] in P.sod:
            if set(t1.by) == set(t2.by) and |t1.by as set| == 1:
                r = единственная роль; path = r.bindings.get(M)
                if path and last_field(M, path).type == many2one:
                    error A11.sod_unsatisfiable {process}
    for P in ir.processes:
        M = P.model; creators = [r for r in roles if Ops(r, M, create) не пусто]
        if not creators: warning A7.no_creator {process}
        if ровно один старт s:
            for r in creators: if not can(r, M, read, s): error A7.creator_read {process, role: r}
    for c in ir.access with c.op == create:
        missing = [f in model(c).fields if f.required and f.type in CHECKED and "default" not in f
                   and f.name not in c.fields and c.role not in parent_fillers(c.model, f.name)]
        if missing: error A7.required_not_creatable {role: c.role, model: c.model}
    for M in ir.models, f in M.fields with f.type == many2one and f.relation — модель приложения T:
        for r in roles:
            if Ops(r, M, read) не пусто and not sees_any(r, T):
                warning A15.related_read {role: r, model: M}
```
