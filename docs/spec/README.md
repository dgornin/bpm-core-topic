# Спецификация ядра: оглавление и общий алгоритм

Спецификация описывает, **что** должно проверять ядро и **какой ответ** оно
выдаёт на каждую конфигурацию. Как это реализовать — решаете вы. Форма
запуска и ответа (команды, JSON, коды выхода) — в [`docs/contract.md`](../contract.md).

Источник истины по распределению кодов по уровням — `tests/levels.json`;
по ожидаемым ответам — `tests/cases/*/expected.json`. Если текст
спецификации и кейс расходятся, откройте issue в репозитории топика.

## Основные понятия

- **IR** (intermediate representation) — JSON-конфигурация приложения,
  которую собрал аналитик в конструкторе (или сгенерировала модель).
  Конфигурация **недоверенная**: в ней может быть что угодно.
- **Нормализация** — проверка документа и ссылок (коды `S1.*`) и заполнение
  значений по умолчанию. Результат — нормализованный IR, с которым работает
  анализ: в нём у каждого узла, перехода, роли и строки прав есть все ключи.
- **Анализ** — проверки смысла нормализованного IR: граф процесса,
  права и участники, действия переходов, политика.
- **Снимок платформы** (`--snapshot`, по умолчанию [`spec/snapshot.json`](../../spec/snapshot.json)) —
  модели, которые уже есть на платформе (пользователи, контакты, проекты):
  на них можно ссылаться, но создавать их конфигурация не может.
- **Пакет политики** (`--policy`) — требования вуза к процессам и правам,
  написанные отдельно от конфигурации («policy as code»).
- **Находка** — код, серьёзность (`error` / `warning` / `unknown`), сообщение,
  место. **Вердикт** — `accept` / `reject` / `unknown` (см. контракт).

## Общий алгоритм `validate`

```text
validate(raw, snapshot, policy?):
    1. ir, findings := normalize(raw, snapshot)            # S1.*, а на уровне A ещё S1.condition, S2.effect, S2.effect_type
       если ir не построен или в findings есть error:
           вернуть findings                                 # вердикт reject, анализ не запускается
    2. cells := итоговые права(ir)                          # раздел 04: явные строки access + неявные права из inputs
       для каждого процесса P в порядке ir.processes:
           структура P                                      # S3.*, S5.no_end (03); A6.no_trigger (03, 3.8 / 04)
           участники P                                      # A14, A6.assignee_no_action, A6.by_read, A4 (04)
           обязательные поля переходов P                    # A5.* (04)
           разделение обязанностей P                        # A11 (04)
       связи процессов через fire                           # S2.fire_not_system, S2.system_unused (05)
       создание документов                                  # A7.* (04)
       самоназначение: права на запись и действия           # A8.* (05)
       видимость связанных записей                          # A15 (04)
       если передана политика: сверка с политикой           # I.* (05)
    3. вердикт по всем находкам: error → reject; иначе unknown → unknown; иначе accept
```

Важные свойства:

1. **Нормализация — фильтр.** Если в ней есть хотя бы одна ошибка, анализ не
   выполняется: в ответе только коды нормализации (`S1.*`, а также
   `S1.condition`, `S2.effect`, `S2.effect_type`), вердикт `reject`. Например,
   при неизвестном виде перехода и одновременно недостижимом узле ответ
   содержит только `S1.flow_kind`.
2. **Внутри нормализации есть ранние остановки.** Если документ не объект,
   у него неверная версия, нет `app.key` или раздел верхнего уровня — не
   список, дальше документ не разбирается. Если после проверки приложения,
   ключей разделов, групп и моделей уже есть ошибки, роли, процессы и права
   не проверяются (им не на что надёжно ссылаться). Подробно — раздел 01, § 11.1.
   Реализация может проверять и больше: лишние коды тестами не штрафуются.
3. **Анализ не останавливается на первой ошибке**: все проверки анализа
   выполняются независимо и собирают все находки. Ошибка структуры
   (например, `S3.unreachable`) не отменяет проверку прав. Исключение: если
   в процессе не ровно один стартовый узел, часть проверок этого процесса
   не выполняется (раздел 03, шаг 1 алгоритма, и раздел 04, § 4.6).
4. **Порядок находок не важен** — тесты его не сравнивают. Порядок шагов выше
   нужен, чтобы понимать зависимости: права (шаг 2) строятся до проверок,
   которые ими пользуются.
5. **`warning` на вердикт не влияет.** Проверок уровня `unknown` в текущей
   версии нет.

## Общий алгоритм `matrix`

```text
matrix(raw, snapshot):
    ir, findings := normalize(raw, snapshot)
    если ir не построен или в findings есть error:
        вернуть findings как validate                      # {"verdict": "reject", ...}, код 1
    вернуть итоговые права(ir), по ячейке на (role, model, op, node)   # раздел 04, код 0
```

Матрица зависит только от нормализации: ошибки анализа (структуры, участников,
политики) на неё не влияют.

## Как читать разделы

Разделы 02–05 для каждого кода дают условие выдачи, серьёзность, ключи
`where` и пример поломки. Кейсы названы по разделам: `ir-*` — нормализация
(01, 02), `st-*` — структура (03), `acc-*` — права и участники (04), `pol-*` —
условия, действия, самоназначение и политика (05), `fix-*` — уточнения
спецификации, добавленные по вопросам пробных реализаций (раздел указан в
`case.json`). Сверяйте понимание текста с кейсами
`tests/cases/`: в `case.json` написано, что не так и почему это ошибка, а
`expected.json` показывает ответ эталона. Если текст можно понять двояко,
ориентируйтесь на кейсы и задайте вопрос в issue.
