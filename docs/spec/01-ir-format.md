# 01. Формат IR v0.1 и нормализация

IR (intermediate representation) — JSON-описание одного low-code приложения:
группы пользователей, модели данных, роли, процессы согласования и матрица прав.
Ядро движка читает IR, **нормализует** его (проверяет схему и заполняет значения
по умолчанию) и только потом передаёт нормализованную копию анализам: структуре
процесса, правам, условиям и действиям, политике вуза.

Этот документ описывает формат целиком и алгоритм нормализации. Все коды находок,
которые выдаёт нормализация (класс `S1.*`), с точными условиями и примерами
перечислены в [02-schema-checks.md](02-schema-checks.md). Условия переходов
(`S1.condition`) и действия (`S2.*`) записываются внутри IR, но их синтаксис и
проверки описаны в [05-conditions-effects-policy.md](05-conditions-effects-policy.md). Структура графа процесса — в
[03-structure.md](03-structure.md), права и команда `matrix` — в
[04-roles-and-access.md](04-roles-and-access.md), форма запуска и ответа — в
[docs/contract.md](../contract.md).

Рабочий пример: [examples/demo_topic.json](../../examples/demo_topic.json) —
согласование темы выпускной работы (черновик → утверждение → опубликована /
отклонена, с возвратом на доработку).

## 1. Файл, кодировка, общие правила

- Файл IR — JSON в кодировке UTF-8 **без BOM**. Если файл не читается, пуст, не
  декодируется как UTF-8 или не является JSON (включая BOM, лишние запятые,
  мусор после значения), команда завершается с кодом 4 и печатает
  `{"error": "..."}` — проверки IR не выполняются ([контракт](../contract.md), кейсы
  [`ir-input-not-json`](../../tests/cases/ir-input-not-json/),
  [`ir-input-empty`](../../tests/cases/ir-input-empty/)).
- Корень документа — JSON-объект. Любой другой корректный JSON (массив, строка,
  число, `null`) — находка `S1.not_object`.
- **Неизвестные ключи игнорируются** во всех объектах, описанных в этом
  документе: это не ошибка и не предупреждение. (Внутри условий вид условия
  определяется набором ключей — см. [05-conditions-effects-policy.md](05-conditions-effects-policy.md).)
- Порядок ключей в объектах не важен. Порядок элементов в списках важен только
  там, где это сказано явно (порядок узлов процесса, позиция ячейки в `access`,
  позиция перехода для `sequence` по умолчанию).
- «Отсутствует» и «равно `null`» — разные вещи: ключ со значением `null`
  считается заданным и проверяется (обычно это ошибка: например, раздел
  `"models": null` — `S1.section`, `"default": null` — `S1.default`). Ровно в
  четырёх местах `null` равносилен отсутствию ключа: `groups[].xmlid`,
  `nodes[].assignee`, `unique[].live_nodes`, `access[].nodes`.
- Все находки нормализации имеют уровень `error`. Предупреждений нормализация не
  выдаёт.

## 2. Лексика: ключи, подписи, имена

Все регулярные выражения ниже применяются к **строке целиком** (полное
совпадение, без допуска завершающего перевода строки), диапазоны `a-z`, `0-9` —
только ASCII. Значение не-строкового типа (число, `true`, `null`, список) не
подходит ни под одно из правил.

| Понятие | Правило | Длина | Где используется |
|---|---|---|---|
| ключ | `[a-z][a-z0-9_]{0,30}` | 1–31 | `app.key`, `key` групп, моделей, ролей, процессов, узлов, переходов; ключи вариантов `selection` |
| подпись | строка без символов с кодом меньше 32 (U+0000–U+001F) | 1–128 символов | `name` приложения, групп, моделей, ролей, процессов, узлов; `label` полей и переходов; подпись варианта `selection`; значение по умолчанию поля `char` |
| имя поля | `x_[a-z0-9_]{1,40}` | 3–42 | `fields[].name` |
| техническое имя модели приложения | `x_[a-z0-9_]+` | не больше 63 | `models[].model` |
| имя внешней модели | `[a-z][a-z0-9_]*(\.[a-z0-9_]+)+` **и** модель есть в снимке платформы | — | `relation` полей |
| xmlid группы Odoo | `[a-z0-9_]+\.[a-z0-9_]+` (ровно одна точка) | — | `groups[].xmlid`, `groups[].implied[]` |

Длина подписи считается в **символах Unicode (кодовых точках)**, а не в байтах:
название из 128 кириллических букв допустимо, хотя в UTF-8 занимает больше
128 байт (кейс [`ir-green-limits`](../../tests/cases/ir-green-limits/)). Пустая
строка — не подпись. Символ U+007F и любые символы с кодом от 32 и выше
допустимы.

## 3. Снимок платформы и служебные поля

Приложение может ссылаться на модели самой платформы (Odoo): пользователей,
контакты, проекты. Какие внешние модели и поля существуют, реализация узнаёт из
**снимка платформы** — JSON-файла вида

```json
{
  "external_models": {
    "res.users": {
      "name": "Пользователь",
      "fields": {
        "name": {"type": "char"},
        "login": {"type": "char"},
        "partner_id": {"type": "many2one", "relation": "res.partner"}
      }
    }
  }
}
```

Снимок по умолчанию лежит в [spec/snapshot.json](../../spec/snapshot.json) и
содержит три модели: `res.users` (поля `name`, `login`, `partner_id` →
`res.partner`), `res.partner` (`name`, `email`) и `project.project` (`name`,
`user_id` → `res.users`, `privacy_visibility`). Опция `--snapshot` заменяет его
целиком.

У **любой** записи (и модели приложения, и внешней модели) есть пять служебных
полей. Они не описываются в IR, но доступны в путях (§ 8.2):

| Поле | Тип | Связь |
|---|---|---|
| `id` | integer | — |
| `create_uid` | many2one | `res.users` (кто создал запись) |
| `write_uid` | many2one | `res.users` (кто правил последним) |
| `create_date` | datetime | — |
| `write_date` | datetime | — |

Служебные поля **не** входят в список полей модели: их нельзя указывать в
`requires`, `inputs`, в `fields` ячеек прав, и они не попадают в раскрытие
«все поля модели» (§ 11.3). Единственное исключение — `create_uid` допустим в
ограничении уникальности (§ 7.3).

## 4. Верхний уровень

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `ir_version` | строка | да | — | версия формата; допустима только строка `"0.1"` (число `0.1` — ошибка) |
| `app` | объект | да | — | приложение (§ 5) |
| `groups` | список объектов | нет | `[]` | группы пользователей (§ 6) |
| `models` | список объектов | нет | `[]` | модели данных (§ 7) |
| `roles` | список объектов | нет | `[]` | роли (§ 8) |
| `processes` | список объектов | нет | `[]` | процессы согласования (§ 9) |
| `access` | список объектов | нет | `[]` | матрица прав (§ 10) |

Раздел, который присутствует, но не является списком (объект, строка, `null`
и т. п.), — ошибка `S1.section`. Минимальный корректный IR:

```json
{"ir_version": "0.1", "app": {"key": "demo", "name": "Демо: пустое приложение"}}
```

(кейс [`ir-green-minimal`](../../tests/cases/ir-green-minimal/)).

Ключи элементов уникальны **внутри своего раздела**; группа и роль с одинаковым
ключом (`head` в демо-примере) не конфликтуют.

## 5. Приложение `app`

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `key` | ключ | да | префикс технических имён: модели приложения по умолчанию называются `x_<app.key>_<model.key>` |
| `name` | подпись | да | название приложения |

## 6. Группы `groups[]`

Группа — набор пользователей Odoo. Права в итоге выдаются группам; роли (§ 8)
опираются на группы.

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | ключ | да | — | ключ группы в IR |
| `name` | подпись | да | — | название |
| `xmlid` | xmlid или `null` | нет | нет | если задан — группа не создаётся, а берётся существующая группа Odoo с этим xmlid (например `base.group_user`) |
| `implied` | список xmlid | нет | `["base.group_user"]`, если `xmlid` не задан (отсутствует или `null`); `[]`, если задан | группы Odoo, которые новая группа включает в себя |

## 7. Модели `models[]`

Модель — тип записей приложения (таблица). Модель, к которой привязан процесс
(§ 9), называется **документом с процессом**: её записи движутся по узлам
процесса.

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | ключ | да | — | ключ модели; по нему на модель ссылаются процессы, права, привязки ролей |
| `name` | подпись | да | — | название |
| `model` | техническое имя | нет | `x_<app.key>_<key>` | имя модели в Odoo (и таблицы в БД) |
| `kind` | `"document"` / `"reference"` | нет | `"document"` | документ (может иметь процесс) или справочник (процесса не имеет) |
| `fields` | список объектов | нет | `[]` | поля (§ 7.1–7.2) |
| `unique` | список объектов | нет | `[]` | ограничения уникальности (§ 7.3) |
| `create_if` | условие | нет | нет | условие, при котором запись можно создать; допустимо только у документа с процессом (формат условия — в [05-conditions-effects-policy.md](05-conditions-effects-policy.md)) |

Имя по умолчанию подставляет ключи как есть, поэтому даже при допустимых ключах
оно может превысить 63 символа: `app.key` и `key` по 31 символу дают имя длиной
65 (кейс [`ir-model-name-default-too-long`](../../tests/cases/ir-model-name-default-too-long/)).
Уникальность технических имён разных моделей не проверяется.

### 7.1. Поля `fields[]`

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `name` | имя поля | да | — | `x_...`; имена `x_active` и `x_studio_state` зарезервированы Odoo |
| `type` | строка | да | — | один из 12 типов ниже |
| `label` | подпись | да | — | подпись поля в интерфейсе |
| `required` | любое | нет | `false` | обязательность; тип значения не проверяется, используется его истинность |
| `default` | зависит от типа | нет | нет | значение по умолчанию; допустимо не для всех типов (§ 7.2) |
| `selection` | список пар `[ключ, подпись]` | для `selection` | — | варианты выбора; у других типов игнорируется |
| `relation` | модель | для связей | — | на какую модель ссылается связь |
| `inverse` | имя поля | для `one2many` | — | обратное поле many2one в целевой модели |
| `ondelete` | строка | нет (только `many2one`) | `"restrict"`, если `required` истинно, иначе `"set null"` | что делать со ссылкой при удалении целевой записи: `restrict`, `set null`, `cascade` |

Типы полей: `char`, `text`, `html`, `integer`, `float`, `boolean`, `date`,
`datetime`, `selection`, `many2one`, `one2many`, `many2many`. Других типов нет
(в том числе `monetary`). Связи (relational) — `many2one`, `one2many`,
`many2many`.

**Поле `x_name` добавляется автоматически.** Если среди полей модели нет объекта
с `"name": "x_name"`, в **начало** списка вставляется
`{"name": "x_name", "type": "char", "label": "Название", "required": true}`.
Если `x_name` описано явно, оно остаётся как есть (с любым допустимым типом).
Поэтому на `x_name` можно ссылаться в `requires`, `unique`, `fields` прав, даже
не описывая его.

**Куда может вести связь (`relation`).** Значение — одно из:

1. ключ модели приложения (`"topic"`);
2. техническое имя модели приложения (`"x_demo_topic"` или явно заданное `model`);
3. имя внешней модели, которая есть в снимке платформы (`"res.users"`).

Модель приложения может быть описана и до, и после поля, которое на неё
ссылается; ссылка на свою же модель допустима. При нормализации `relation` на
модель приложения заменяется её **техническим именем** (`"topic"` →
`"x_demo_topic"`). `one2many` допускается только на модели приложения, и у
целевой модели должно быть поле с именем `inverse` типа `many2one` (на какую
модель ведёт это поле, не проверяется). `relation`, `inverse`, `ondelete` у
полей других типов игнорируются (`ondelete` — у всех типов, кроме `many2one`).

**Неоднозначные имена моделей — вне контракта.** Правило выше однозначно, пока
технические имена моделей приложения различны и ни один ключ модели не
совпадает с техническим именем другой модели (ключ вида `x_demo_note`
допустим). Нормализация такие совпадения не проверяет и находок на них не
выдаёт (раздел 02, «Чего проверки схемы не делают»). На какую модель тогда
ведут `relation` и пути через такое поле, не определено, тестов на это нет.
Корректная конфигурация так не делает.

### 7.2. Значения по умолчанию полей (`default`)

Если ключ `default` присутствует (даже со значением `null`), значение должно
подходить типу поля:

| Тип поля | Допустимое значение `default` |
|---|---|
| `char` | подпись (непустая строка до 128 символов без управляющих символов) |
| `integer` | целое JSON-число, записанное без точки и экспоненты; `true`/`false` не считаются числами, `3.0`, `1e2` и `"3"` не подходят |
| `boolean` | `true` или `false` |
| `selection` | строка, равная ключу одного из вариантов `selection` |
| все остальные (`text`, `html`, `float`, `date`, `datetime`, связи) | никакое: `default` у них запрещён |

### 7.3. Уникальность `unique[]`

Ограничение уникальности — объект:

| Ключ | Тип | Обязателен | Смысл |
|---|---|---|---|
| `fields` | непустой список имён полей | да | набор полей, значения которых не должны повторяться у двух записей (записи, где хоть одно из полей пусто, не учитываются) |
| `live_nodes` | непустой список ключей узлов или `null` | нет | если задан — уникальность действует только среди документов, находящихся в этих узлах процесса модели |

В `fields` допустимы поля, описанные в модели (включая автоматическое `x_name`),
и служебное `create_uid`; поля типов `one2many`, `many2many`, `text`, `html`
недопустимы (уникальность реализуется индексом БД). `live_nodes` допустим только
у модели, к которой привязан процесс, и только с ключами узлов этого процесса.

## 8. Роли `roles[]`

Роль — «кто это по отношению к документу»: автор, заведующий, руководитель
проекта. Роль включает пользователей своих групп; привязки (`bindings`) сужают
её до конкретных записей.

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | ключ | да | — | ключ роли |
| `name` | подпись | да | — | название |
| `groups` | непустой список ключей групп IR | да | — | группы, на которые опирается роль; это ключи из `groups[]`, а не xmlid Odoo |
| `see_all` | любое | нет | `false` | роль видит все записи независимо от привязок; тип не проверяется |
| `bindings` | объект `{ключ модели: путь}` | нет | `{}` | для каждой модели — путь к полю-пользователю записи |

### 8.1. Групповые и привязанные роли

- **Групповая роль** — `bindings` пуст. Её держит каждый пользователь её групп,
  и на любой записи. Пример: `head` в демо.
- **Привязанная роль** — `bindings` не пуст. На записи модели `M` роль держит
  только пользователь (пользователи), до которого ведёт путь `bindings[M]` от
  этой записи. Пример: `author` с `{"topic": "create_uid"}` — автор темы тот, кто
  её создал.

Ключом в `bindings` служит **ключ модели приложения** (не техническое имя и не
внешняя модель). Путь должен оканчиваться полем типа `many2one` или `many2many`,
ведущим ровно на `res.users`; путь не может проходить через `write_uid` (тот, кто
правил запись последним, — это любой нажавший кнопку, роль «перетекала» бы к
нему). Привязанная роль может получать права (кроме `create`) только на модели,
перечисленные в её `bindings` (§ 10).

### 8.2. Пути по полям

Путь — непустая строка из имён полей через точку: `"create_uid"`,
`"x_project_id.user_id"`. Он разрешается от модели `M`:

```
текущая := M
для каждого имени n_i в path.split("."):
    поля := поля модели «текущая» (описанные в IR, включая x_name, + служебные поля § 3;
            для внешней модели — поля из снимка + служебные поля)
    если модели «текущая» нет или n_i нет среди полей → путь неверен
    если n_i не последнее:
        если тип поля не связь (many2one / one2many / many2many) → путь неверен
        текущая := модель, на которую ведёт relation поля
последнее поле пути — результат
```

Промежуточными могут быть связи любого вида (в том числе `one2many`), конечное
поле — любое; ограничения на конечное поле задаёт место использования (для
привязки роли — ссылка на `res.users`). Пустая строка и не-строка — неверный путь.

## 9. Процессы `processes[]`

Процесс — граф согласования, по которому движутся документы одной модели.

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | ключ | да | — | ключ процесса |
| `name` | подпись | да | — | название |
| `model` | ключ модели приложения | да | — | модель-документ; ровно по ключу, не по техническому имени; модель должна иметь `kind` = `document`; у модели не больше одного процесса |
| `nodes` | список объектов | нет | `[]` | узлы (§ 9.1) |
| `flows` | список объектов | нет | `[]` | переходы (§ 9.2) |
| `sod` | список пар ключей переходов | нет | `[]` | разделение обязанностей (§ 9.3) |

### 9.1. Узлы `nodes[]`

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | ключ | да | — | ключ узла, уникален в процессе |
| `name` | подпись | да | — | название этапа |
| `type` | `"step"` / `"xor"` / `"end"` | нет | `"step"` | шаг (работа людей), развилка (автоматический выбор ветки), завершение |
| `start` | любое | нет | `false` | стартовый узел (тип не проверяется; сколько стартов — проверка структуры) |
| `assignee` | ключ роли или `null` | нет | нет | исполнитель шага: кому шаг попадает в задачи; задаётся только у `step` |
| `result` | `"done"` / `"rejected"` / `"cancelled"` | нет (только `end`) | `"done"` у `end` | итог завершения; у узлов других типов не проверяется и не заполняется |
| `release` | список ключей ролей | нет | `[]` | роли, которые в этом узле намеренно теряют доступ к документу |

Порядок узлов в списке — **порядок процесса**: в нём раскрываются и
упорядочиваются узлы в правах (§ 11.3).

### 9.2. Переходы `flows[]`

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `key` | ключ | да | — | ключ перехода, уникален в процессе |
| `label` | подпись | нет | значение `key` | надпись на кнопке |
| `from`, `to` | ключ узла | да | — | откуда и куда ведёт переход |
| `by` | список ключей ролей | нет | `[]` | кто может нажать |
| `auto` | любое | нет | `false` | автоматический переход (выход развилки) |
| `system` | любое | нет | `false` | системный переход: выполняется действием `fire` другого процесса, а не человеком |
| `kind` | `"normal"` / `"return"` | нет | `"normal"` | `return` — возврат на доработку |
| `comment` | `"none"` / `"optional"` / `"required"` | нет | `"none"` | нужен ли комментарий при переходе |
| `default` | любое | нет | `false` | выход развилки по умолчанию |
| `sequence` | целое число | нет | `(позиция + 1) * 10` | порядок перехода (кнопок, проверки выходов развилки) |
| `requires` | список имён полей | нет | `[]` | поля, которые должны быть заполнены, чтобы переход был доступен |
| `inputs` | список имён полей | нет | `[]` | поля, которые нажимающий заполняет в диалоге перехода (не списки) |
| `notify` | список ключей ролей | нет | `[]` | кого уведомить о переходе |
| `condition` | условие | нет | нет (ключ остаётся отсутствующим) | условие перехода — см. [05-conditions-effects-policy.md](05-conditions-effects-policy.md) |
| `effects` | список действий | нет | `[]` | действия `fire` / `set` / `create` / `subscribe` — см. [05-conditions-effects-policy.md](05-conditions-effects-policy.md) |

`позиция` — индекс перехода в исходном списке `flows` (с нуля), включая
переходы с ошибками: первый переход получает 10, второй 20 и т. д. `sequence`
сравнивается строго как целое: `"40"`, `40.0`, `true` — ошибка. Отрицательные
значения и повторы допустимы.

Поля `requires` и `inputs` — поля модели процесса, описанные в IR (включая
автоматическое `x_name`); служебные поля не допускаются. В `inputs` нельзя
указывать `one2many` и `many2many`; в `requires` — можно.

### 9.3. Разделение обязанностей `sod`

Каждый элемент `sod` — список ровно из двух ключей переходов **этого** процесса:
`[["submit", "approve"]]` означает, что `submit` и `approve` одного документа
должны выполнять разные люди. На уровне схемы проверяется только форма пары и
существование переходов (совпадающие ключи в паре — забота анализа прав).

## 10. Матрица прав `access[]`

Ячейка выдаёт роли операцию над записями модели приложения.

| Ключ | Тип | Обязателен | По умолчанию | Смысл |
|---|---|---|---|---|
| `role` | ключ роли | да | — | кому (только роль, не группа) |
| `model` | ключ модели приложения | да | — | над чем (только ключ, не техническое имя; на внешние модели права не выдаются) |
| `op` | `"read"` / `"write"` / `"create"` / `"unlink"` | да | — | операция |
| `nodes` | непустой список ключей узлов или `null` | нет | все узлы процесса модели (если процесс есть и `op` ≠ `create`) | в каких узлах документа действует право |
| `fields` | список имён полей модели | нет (только `write`/`create`) | все поля модели | какие поля можно записывать; пустой список допустим |

Правила:

- `nodes` допустим только для модели с процессом; список должен быть непустым и
  состоять из ключей узлов её процесса.
- У `create` не бывает `nodes`: запись создаётся до старта процесса.
- `fields` у `read` и `unlink` игнорируется.
- Привязанная роль (с непустыми `bindings`) получает `read`, `write`, `unlink`
  только на модели, перечисленные в её `bindings`; `create` — на любые.
  `see_all` это правило не отменяет.

Смысл ячейки: пользователь, который держит роль на записи (§ 8.1), может
выполнять `op` над этой записью, пока документ находится в одном из `nodes`.
Права на запись полей, которые неявно дают `inputs` переходов, добавляются не
нормализацией, а при построении матрицы (см.
[04-roles-and-access.md](04-roles-and-access.md)).

## 11. Нормализация

### 11.1. Порядок этапов и точки останова

Нормализация — последовательность этапов. Находки накапливаются; в **точках
останова** нормализация прекращается, если к этому моменту есть хотя бы одна
ошибка. Если нормализация прекратилась, IR считается ненормализуемым:
`validate` возвращает `reject` со всеми накопленными находками, анализ
(структура, права, условия, политика) **не выполняется**, `matrix` печатает тот же
JSON, что `validate`, с кодом 1.

| № | Этап | Коды | Что дальше при ошибке |
|---|---|---|---|
| 0 | корень — объект | `S1.not_object` | стоп сразу |
| 1 | `ir_version` = строка `"0.1"` | `S1.version` | стоп сразу |
| 2 | `app` — объект, `app.key` — ключ | `S1.app` | стоп сразу |
| 2a | `app.name` — подпись | `S1.label` | продолжить |
| 3 | разделы `groups`, `models`, `roles`, `processes`, `access` (в этом порядке): отсутствует → `[]`; не список → ошибка | `S1.section` | стоп сразу на **первом** неверном разделе |
| 4 | ключи элементов `groups`, `models`, `roles`, `processes` | `S1.key`, `S1.duplicate` | продолжить |
| 5 | группы | `S1.label`, `S1.xmlid` | продолжить |
| 6 | модели и поля, первая часть `unique` | `S1.model_name`, `S1.label`, `S1.model_kind`, `S1.field`, `S1.field_name`, `S1.duplicate`, `S1.field_type`, `S1.default`, `S1.selection`, `S1.relation`, `S1.inverse`, `S1.ondelete`, `S1.unique` | продолжить |
| **A** | **точка останова A** | | стоп, если есть ошибки этапов 2a–6 |
| 7 | роли | `S1.label`, `S1.role_groups`, `S1.binding` | продолжить |
| 8 | процессы: модель, узлы, переходы (с условиями и действиями), `sod`; затем «один процесс на модель» | `S1.process_model`, `S1.label`, `S1.node`, `S1.node_type`, `S1.role_ref`, `S1.assignee`, `S1.result`, `S1.flow`, `S1.flow_node`, `S1.flow_kind`, `S1.comment`, `S1.field_ref`, `S1.sod`, а также `S1.condition`, `S2.*` | продолжить |
| 9 | `create_if` моделей | `S1.create_if` (и `S1.condition`) | продолжить |
| 10 | вторая часть `unique`: типы полей, `live_nodes` | `S1.unique` | продолжить |
| 11 | `access` | `S1.access` | продолжить |
| **B** | **точка останова B** | | стоп, если есть ошибки этапов 7–11 |

Следствия, которые важны для реализации:

- Ошибка в моделях или полях (этапы 4–6) скрывает все ошибки ролей, процессов и
  прав: например, при неподдерживаемом типе поля и неизвестной роли в `access`
  выдаётся только `S1.field_type`.
- Внутри этапов 4–6 и внутри этапов 7–11 проверяются **все** элементы, находки
  не прерывают проверку соседних элементов.
- После точки A все элементы `groups`, `models`, `roles`, `processes` — объекты с
  корректными уникальными ключами, а все поля моделей корректны. Этапы 7–11
  могут на это опираться.
- «Процесс модели» на этапах 9–11 — процесс, у которого `model` равен ключу
  модели (если таких несколько, это уже ошибка этапа 8; берётся последний в
  списке). «Узлы процесса модели» здесь (и в условиях и действиях этапа 8) —
  значения `key` **всех** узлов этого процесса как записаны, в том числе узлов
  с находкой `S1.node`. При такой находке нормализация всё равно закончится
  ошибкой, так что разница видна только в лишних кодах.

Внутри элемента проверки идут в порядке таблиц §§ 5–10; там, где проверка
элемента прерывается раньше (например, поле с неверным именем дальше не
проверяется), это сказано у соответствующего кода в
[02-schema-checks.md](02-schema-checks.md).

### 11.3. Упорядочивание и удаление повторов

- `roles[].groups`, а также `by`, `requires`, `inputs`, `notify` переходов и
  `release` узлов: повторы удаляются, элементы сортируются по возрастанию
  (обычное сравнение строк по кодовым точкам).
- `flows` процесса сортируются по `sequence` по возрастанию; при равных
  `sequence` сохраняется исходный порядок (устойчивая сортировка).
- `nodes` ячейки прав: повторы удаляются, порядок — **порядок узлов процесса**
  (а не порядок в ячейке): `["rejected", "review", "published", "review"]` →
  `["review", "published", "rejected"]` для демо-процесса.
- `fields` ячейки `write`/`create`: повторы удаляются, сортировка по имени.
- Порядок самих ячеек `access`, моделей, ролей, процессов, узлов не меняется.

Пример: демо-права после нормализации (сравните с исходными в
[examples/demo_topic.json](../../examples/demo_topic.json)):

```json
[
  {"role": "author", "model": "topic", "op": "create", "fields": ["x_description", "x_name"]},
  {"role": "author", "model": "topic", "op": "read", "nodes": ["draft", "review", "published", "rejected"]},
  {"role": "author", "model": "topic", "op": "write", "nodes": ["draft"], "fields": ["x_description", "x_name"]},
  {"role": "author", "model": "topic", "op": "unlink", "nodes": ["draft"]},
  {"role": "head", "model": "topic", "op": "read", "nodes": ["review", "published", "rejected"]},
  {"role": "student", "model": "topic", "op": "read", "nodes": ["published"]}
]
```

Значения по умолчанию и упорядочивание проверяются «зелёными» кейсами
[`ir-green-features`](../../tests/cases/ir-green-features/) (нет `x_name`, связи
по ключу и по техническому имени, путь привязки через внешнюю модель, права без
`nodes`/`fields`, узлы вразнобой и с повтором, переходы не по порядку `sequence`)
и [`ir-green-limits`](../../tests/cases/ir-green-limits/) (значения ровно на
границах длин).

### 11.4. Что получает анализ

Если обе точки останова пройдены, нормализованный IR (со всеми значениями по
умолчанию, раскрытыми `nodes`/`fields`, отсортированными списками) передаётся
анализам. Сами по себе ошибок нормализация больше не добавляет; вердикт
складывается из находок нормализации и анализов: есть хоть одна находка уровня
`error` → `reject`; иначе есть `unknown` → `unknown`; иначе `accept`
(предупреждения `warning` вердикт не меняют).
