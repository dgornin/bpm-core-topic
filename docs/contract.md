# Контракт реализации (CLI)

Этот документ — точное описание того, как реализацию запускают и что она
должна ответить. По нему работают приёмочные тесты (`tests/run_acceptance.py`),
эксперт и закрытый стенд автора. Контракт одинаков для эталонной реализации
автора и для вашей. Что именно проверять — в спецификации `docs/spec/`;
здесь — только форма входа и выхода.

## Команды

```text
<impl> validate IR.json [--policy PACK.json] [--snapshot SNAP.json]
<impl> matrix   IR.json [--snapshot SNAP.json]
```

`<impl>` — команда запуска реализации. Для скелета на Python это
`python -m bpmcore` (из корня репозитория) или `bpmcore` после `pip install -e .`.

| Аргумент | Что это | Формат |
|---|---|---|
| `IR.json` | конфигурация приложения (IR) | `docs/spec/01-ir-format.md` |
| `--policy PACK.json` | пакет политики вуза (только `validate`) | `docs/spec/05-conditions-effects-policy.md` |
| `--snapshot SNAP.json` | снимок платформы: внешние модели | по умолчанию — `spec/snapshot.json` |

Пути — относительно текущего каталога. Все файлы читаются в UTF-8 (без BOM).
Порядок опций произвольный; других аргументов нет.

**Снимок по умолчанию.** Если `--snapshot` не указан, используется снимок из
`spec/snapshot.json` (внешние модели `res.users`, `res.partner`,
`project.project`). В скелете он встроен в `bpmcore/snapshot.py`; в реализации
на другом языке встройте его так же или читайте файл.

## Вывод

В stdout печатается **ровно один JSON-объект** в UTF-8 и ничего больше
(отладочный вывод — только в stderr). Отступы и порядок ключей — любые.

### `validate`

```json
{
  "verdict": "reject",
  "findings": [
    {
      "code": "S3.unreachable",
      "level": "error",
      "message": "Узел недостижим от старта.",
      "where": {"process": "topic", "node": "published"}
    }
  ]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `verdict` | `"accept"` \| `"reject"` \| `"unknown"` | итог проверки, см. «Вердикт» |
| `findings` | массив | находки в любом порядке; пустой, если замечаний нет |
| `findings[].code` | строка | код проверки из спецификации, например `S3.unreachable` (полный список — `tests/levels.json`) |
| `findings[].level` | `"error"` \| `"warning"` \| `"unknown"` | серьёзность |
| `findings[].message` | строка | понятное аналитику сообщение (по-русски) |
| `findings[].where` | объект | где искать ошибку: `process`, `node`, `flow`, `role`, `model`, `field`, `cell`… (набор ключей свободный) |

Если один дефект встречается в нескольких местах (например, три недостижимых
узла), выдайте находку на каждое место.

Используйте только коды из спецификации. Лишние коды тестами не штрафуются,
но это ложные срабатывания: аналитик увидит замечание, которого нет.

### `matrix`

Если IR нормализуется (нет ошибок схемы S1):

```json
{
  "cells": [
    {"role": "author", "model": "topic", "op": "create", "node": "*", "fields": ["x_description", "x_name"]},
    {"role": "author", "model": "topic", "op": "read", "node": "draft"},
    {"role": "author", "model": "topic", "op": "write", "node": "draft", "fields": ["x_description", "x_name"]}
  ]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `role` | строка | ключ роли |
| `model` | строка | ключ модели |
| `op` | `"read"` \| `"write"` \| `"create"` \| `"unlink"` | операция |
| `node` | строка | ключ узла процесса; `"*"` — если у модели нет процесса или `op` = `create` |
| `fields` | массив строк | только для `write` и `create`: отсортированное объединение полей |

Правила:

- одна запись на четвёрку `(role, model, op, node)`; если право на одну и ту
  же четвёрку получено несколькими способами, их поля объединяются;
- учитываются и явные права раздела `access`, и **неявные права на запись**,
  которые дают входы переходов (`inputs`) — `docs/spec/04-roles-and-access.md`;
- записи отсортированы по `(role, model, op, node)`, `fields` — по алфавиту;
- у `read` и `unlink` ключа `fields` нет.

Если IR не нормализуется, `matrix` отвечает тем же JSON, что и `validate`
(`{"verdict": "reject", "findings": [...]}`), и завершается с кодом 1.

### Ошибка входа

Если файл (IR, политика или снимок) не читается или не является JSON:

```json
{"error": "ir.json: некорректный JSON (Expecting value: line 1 column 1 (char 0))"}
```

Текст ошибки — любой понятный. Обратите внимание: корректный JSON, который
не является объектом (например, `[]` или `42`), — **не** ошибка входа, а
находка `S1.not_object` с вердиктом `reject`.

## Вердикт

1. Есть хотя бы одна находка уровня `error` → `reject`.
2. Иначе есть хотя бы одна находка уровня `unknown` → `unknown`.
3. Иначе → `accept`.

Находки `warning` на вердикт не влияют: конфигурация с одними
предупреждениями принимается (`accept`). В текущей версии спецификации нет
проверок с уровнем `unknown`; уровень и код выхода 3 зарезервированы.

## Коды выхода

| Код | Когда | stdout |
|---|---|---|
| 0 | `validate`: вердикт `accept`; `matrix`: матрица построена | `{"verdict": ...}` / `{"cells": ...}` |
| 1 | вердикт `reject` (в том числе `matrix` на ненормализуемом IR) | `{"verdict": "reject", ...}` |
| 2 | ошибка аргументов командной строки (так завершается `argparse`) | сообщение в stderr |
| 3 | вердикт `unknown` | `{"verdict": "unknown", ...}` |
| 4 | ошибка входа: файл не читается или не JSON | `{"error": "..."}` |

Падение реализации (необработанное исключение) — не код из таблицы: тест
считается непройденным.

## Как сравнивают тесты

Каждый кейс — каталог `tests/cases/<имя>/`. Раннер запускает реализацию
**в каталоге кейса**: `<impl> <command> <args...>`, где `command` и `args`
взяты из `expected.json` (например, `validate ir.json --policy policy.json`).
Таймаут — 20 секунд на кейс.

| Что | Правило |
|---|---|
| код выхода | точное совпадение |
| `verdict` | точное совпадение |
| коды находок | все коды из `expected.json` (`codes`) должны быть среди выданных; лишние коды не штрафуются |
| `matrix` | точное совпадение множества ячеек (включая `fields`); повторяющиеся ячейки — ошибка |
| ошибка входа | код 4 и объект с ключом `error` |
| `message`, `where`, порядок находок | не сравниваются |

`codes` — множество кодов, которые на этом кейсе выдаёт эталонная реализация
(уровней `error` и `warning`). Каждый код достаточно выдать хотя бы один раз.

### Файлы кейса

| Файл | Кто пишет | Содержимое |
|---|---|---|
| `case.json` | автор кейса | `title`, `description` (что не так и почему это ошибка), `command`; у кейса на ошибку входа может быть `level` (кодов нет, уровень из них не вывести) |
| `ir.json` | автор кейса | вход; может быть намеренно битым, в том числе не-JSON |
| `policy.json` | автор кейса | пакет политики (необязателен, только для `validate`) |
| `expected.json` | **только генератор** по эталону | см. ниже |

```json
{
  "command": "validate",
  "args": ["ir.json"],
  "exit_code": 1,
  "verdict": "reject",
  "codes": ["S3.unreachable"],
  "level": "C"
}
```

- `verdict` и `codes` — у кейсов `validate` и у `matrix` на ненормализуемом IR;
- `cells` — у кейсов `matrix` с построенной матрицей;
- у кейсов на ошибку входа есть только `command`, `args`, `exit_code`, `level`;
- `level` — уровень кейса: наибольший уровень среди его кодов
  (`tests/levels.json`); кейс без кодов — уровень C; кейс `matrix` — не ниже B.

`python tests/run_acceptance.py --level B` запускает кейсы уровней C и B,
`--level A` — все.

## Переменная `BPM_IMPL`

Раннер берёт команду реализации из переменной окружения `BPM_IMPL`
(разбирается как командная строка shell). По умолчанию — `python -m bpmcore`
тем же интерпретатором, которым запущен раннер; корень репозитория
добавляется в `PYTHONPATH`, поэтому пакет находится из каталога кейса.

```bash
make test-all                                          # скелет на Python
BPM_IMPL="./target/release/bpmcore" make test-all      # Rust, Go, C++ ...
BPM_IMPL="java -jar build/bpmcore.jar" make test-all   # JVM
BPM_IMPL="node dist/cli.js" python tests/run_acceptance.py --level C
```

Windows (PowerShell): `$env:BPM_IMPL = "node dist/cli.js"; py tests\run_acceptance.py`.

Относительные пути в `BPM_IMPL` (`main.py`, `./build/bpmcore`, `dist/cli.js`)
считаются от каталога, из которого запущен раннер (обычно корень
репозитория); имя модуля после `-m` (`python3 -m bpmcore`) остаётся именем.
Если вы пишете не на Python, укажите в `README_SOLUTION.md` команды сборки и
точное значение `BPM_IMPL`.
