> JSON-описание процесса согласования (кто создаёт документ, какие шаги он

## Зачем это

В вузе десятки процессов согласования: темы ВКР, заявки на отпуск,
командировки, служебные записки. Каждый — это документ, который проходит
шаги (черновик → на утверждении → утверждён/отклонён), и на каждом шаге
разные люди должны видеть и править разное. Программировать каждый процесс
вручную дорого, поэтому их собирают в **low-code BPM-конструкторе**:
аналитик (или языковая модель по описанию на естественном языке) составляет
**JSON-конфигурацию** — IR, — а движок по ней создаёт модели данных, права
доступа и кнопки переходов.

Проблема в том, что **конфигурация недоверенная**. В ней легко ошибиться так,
что процесс формально запускается, но:

- документ застревает в шаге, из которого нет выхода, или ходит по кругу;
- исполнитель шага не видит документ, который должен утвердить;
- после отправки на согласование автор теряет доступ к собственной заявке;
- участник может сам вписать себя в поле «руководитель» и утвердить свою же заявку;
- роль «студент» видит черновики, хотя по положению вуза — только опубликованное.

Такие ошибки нужно ловить **до** того, как конфигурация попадёт в работу, —
статически, по одному JSON, без базы данных и без запуска процесса. Это и
делает ядро-валидатор. **Ваша задача — написать такое ядро** по готовой
спецификации и пройти приёмочные тесты.

Почему это интересно:

- **графы**: достижимость, тупики, гарантированное завершение, обязательные
  ступени, которые нельзя обойти;
- **права доступа**: из декларативного описания ролей и правил строится
  итоговая матрица прав и проверяется её согласованность с процессом;
- **статический анализ**: недоверенный вход, нормализация, коды находок,
  отсутствие каскада ложных ошибок — как в настоящем линтере или компиляторе;
- **policy as code**: требования вуза записаны отдельным машинно-проверяемым
  пакетом политики, и конфигурация сверяется с ним автоматически.

Опыт работы с Odoo, BPMN или конкретным BPM-движком **не нужен**: всё, что
нужно знать о предметной области, есть в спецификации.

## Что должно получиться

Консольная утилита с двумя командами по контракту [`docs/contract.md`](docs/contract.md):

```text
bpmcore validate IR.json [--policy PACK.json] [--snapshot SNAP.json]
bpmcore matrix   IR.json [--snapshot SNAP.json]
```

Она проходит приёмочные тесты уровней C, B и A (`tests/cases/`, более 200 кейсов).
Язык по умолчанию — Python ≥ 3.10 без внешних зависимостей (в репозитории
есть скелет); можно и другой язык — см. [FAQ](#faq).

Пример — корректная конфигурация согласования темы
([`examples/demo_topic.json`](examples/demo_topic.json)): автор пишет тему,
заведующий утверждает, отклоняет или возвращает на доработку, студенты
видят только опубликованные темы.

```console
$ python -m bpmcore validate examples/demo_topic.json
{
  "verdict": "accept",
  "findings": []
}
$ echo $?
0
```

Та же конфигурация с одной ошибкой
([`examples/topic_broken.json`](examples/topic_broken.json)): переход
«Утвердить» по ошибке ведёт обратно в черновик (`"to": "draft"` вместо
`"to": "published"`), и до узла «Опубликована» больше нельзя дойти:

```console
$ python -m bpmcore validate examples/topic_broken.json
{
  "verdict": "reject",
  "findings": [
    {
      "code": "S3.unreachable",
      "level": "error",
      "message": "Узел недостижим от старта.",
      "where": {"process": "topic", "node": "published"}
    }
  ]
}
$ echo $?
1
```

С пакетом политики вуза ([`examples/policies/demo_topic.json`](examples/policies/demo_topic.json)):
если в конфигурации студенту дали чтение темы на всех шагах
([`examples/topic_students_see_all.json`](examples/topic_students_see_all.json):
у строки прав `student` убраны `nodes`), а политика разрешает только
опубликованные, —

```console
$ python -m bpmcore validate examples/topic_students_see_all.json --policy examples/policies/demo_topic.json
{
  "verdict": "reject",
  "findings": [
    {
      "code": "I.excess",
      "level": "error",
      "message": "Избыточные права: роль 'student' получает read на 'topic' сверх разрешённого политикой (draft, rejected, review).",
      "where": {"role": "student", "model": "topic"}
    }
  ]
}
```

Матрица прав демо-конфигурации (начало):

```console
$ python -m bpmcore matrix examples/demo_topic.json
{
  "cells": [
    {"role": "author", "model": "topic", "op": "create", "node": "*", "fields": ["x_description", "x_name"]},
    {"role": "author", "model": "topic", "op": "read", "node": "draft"},
    {"role": "author", "model": "topic", "op": "read", "node": "published"},
    {"role": "author", "model": "topic", "op": "read", "node": "rejected"},
    {"role": "author", "model": "topic", "op": "read", "node": "review"},
    {"role": "author", "model": "topic", "op": "unlink", "node": "draft"},
    {"role": "author", "model": "topic", "op": "write", "node": "draft", "fields": ["x_description", "x_name"]},
    {"role": "head", "model": "topic", "op": "read", "node": "published"},
    ...
  ]
}
```

(Вывод здесь сокращён и чуть переформатирован; это ответы эталонной
реализации автора. Сообщения `message` у вас могут быть другими — тесты их
не сравнивают.)

## Быстрый старт

Нужен Python 3.10+ и git. Подробности для macOS / Linux / Windows и решение
частых проблем — [`docs/00-setup.md`](docs/00-setup.md).

```bash
# 1. Форк (или «Use this template») на GitHub, затем:
git clone <URL-вашего-форка> bpm-core
cd bpm-core

# 2. (необязательно) виртуальное окружение — зависимостей всё равно нет
python3 -m venv .venv && source .venv/bin/activate

# 3. Скелет запускается
python3 -m bpmcore validate examples/demo_topic.json

# 4. Тесты уровня C
make test-c
```

Без `make` (Windows):

```powershell
py tests\run_acceptance.py --level C
py -m bpmcore validate examples\demo_topic.json
```

**Что вы увидите на старте.** Скелет работает, но ничего не проверяет: на
любую конфигурацию отвечает `accept`. Поэтому проходят только «зелёные»
кейсы (корректные конфигурации) и кейсы на нечитаемый файл, а все кейсы с
ошибками красные — **так и задумано**. Отчёт раннера показывает для каждого
красного кейса, что в нём сломано, что ожидалось и что получено, а в конце —
итог вида `C: 35/85, B: 1/71, A: 0/68`. Раннер при этом завершается с кодом 1,
и `make` дописывает `make: *** [test-c] Error 1` — это значит «есть
непрошедшие кейсы», а не сбой установки.

Что в скелете уже готово, а что нужно написать:

| Модуль | Состояние | Что внутри |
|---|---|---|
| `bpmcore/cli.py` | готов | разбор аргументов, чтение JSON, коды выхода, вывод, сборка ответа `matrix` |
| `bpmcore/findings.py` | готов | находки и вердикт |
| `bpmcore/validate.py` | готов | порядок проверок (можно менять) |
| `bpmcore/snapshot.py` | готов | снимок платформы по умолчанию |
| `bpmcore/normalize.py` | **заглушка** | нормализация и проверки схемы S1 |
| `bpmcore/structure.py` | **заглушка** | граф процесса: S3, S5 |
| `bpmcore/access.py` | **заглушка** | матрица прав, участники: A4–A7, A11, A14, A15 |
| `bpmcore/conditions.py` | **заглушка** | условия: S1.condition |
| `bpmcore/effects.py` | **заглушка** | действия переходов (effects) и самоназначение: S2, A8 |
| `bpmcore/policy.py` | **заглушка** | политика вуза: I.* |

Структуру скелета можно менять как угодно (добавлять модули, переписывать
готовые части) — важно только соблюдать контракт CLI. **Каталог `tests/`
менять нельзя**; свои тесты кладите отдельно (например, в `unit_tests/`).

## Задание по шагам: уровни C → B → A

Каждый уровень — законченный результат: после уровня C у вас работающий
валидатор структуры процессов, после B — ещё и прав доступа, после A — полный
валидатор с политикой вуза. Уровни накопительные: `make test-b` запускает
кейсы C и B, `make test-a` — все. Распределение кодов по уровням —
[`tests/levels.json`](tests/levels.json) и таблица в
[`docs/spec/README.md`](docs/spec/README.md).

Оценки трудоёмкости — для магистранта, уверенно пишущего на Python, включая
чтение спецификации и отладку на кейсах. Часы — оценка автора. Соотношение
уровней и самые трудные места уточнены по двум пробным реализациям, сделанным
только по тексту этого репозитория. Доли работы C : B : A у них —
примерно 40 : 20 : 40. Уровень B после C идёт быстро, потому что большая часть
нормализации к этому моменту уже написана. Самое плотное место — § 5.6
(самоназначение через действия переходов).

**Совет, проверенный на пробных реализациях:** сначала прочитайте спецификацию
целиком (01–05, хотя бы бегло), потом пишите код. Нормализацию удобно сразу
писать всю (этапы 0–11 раздела 01, § 11.1, с точками останова A и B), а
проверки, которые «не ваш уровень», оставлять заглушками.

### Уровень C — структура и ссылки процесса (≈ 10–12 ч)

1. **Разобраться (≈ 2–3 ч).** Прочитайте этот README, [`docs/contract.md`](docs/contract.md),
   [`docs/spec/README.md`](docs/spec/README.md) (общий алгоритм) и
   [`docs/spec/01-ir-format.md`](docs/spec/01-ir-format.md). Запустите скелет
   и `make test-c`, посмотрите на пару красных кейсов.
2. **Нормализация, базовая часть (≈ 4–5 ч)** — `bpmcore/normalize.py` по
   [`docs/spec/02-schema-checks.md`](docs/spec/02-schema-checks.md):
   документ целиком (`S1.not_object`, `S1.version`, `S1.app`, `S1.section`),
   ключи и дубликаты, процессы, узлы, переходы, ссылки на роли, SoD; значения
   по умолчанию для узлов и переходов. **Уже на уровне C** нужно обходить и
   модели: `S1.duplicate` ловит и повторное имя поля модели (кейс
   `ir-duplicate-field`), `S1.label` (уровень C) проверяет подписи групп,
   моделей, полей и ролей, а `S1.process_model` смотрит на ключ и вид (`kind`)
   модели. Разбирать типы полей, связи и права для этого не нужно.
3. **Структура процесса (≈ 3–4 ч)** — `bpmcore/structure.py` по
   [`docs/spec/03-structure.md`](docs/spec/03-structure.md): старт, концы,
   достижимость, тупики, развилки, возвраты, гарантированное завершение
   (`S3.*`, `S5.no_end`).
4. **`make test-c` зелёный.** Зафиксируйте коммит — это уже оценка C.

### Уровень B — данные, роли, права, `matrix` (≈ +5–7 ч)

5. **Нормализация, остальное (≈ 2–3 ч)** — модели и поля, группы, роли и их
   привязки к записям, ссылки на поля в переходах, раздел прав с раскрытием
   узлов и полей по умолчанию ([`02-schema-checks.md`](docs/spec/02-schema-checks.md)).
6. **Матрица прав (≈ 1 ч)** — `access.effective_cells` и команда `matrix`
   по [`docs/spec/04-roles-and-access.md`](docs/spec/04-roles-and-access.md),
   включая неявные права на запись из `inputs` переходов.
7. **Участники и права (≈ 2–3 ч)** — `access.check_access`: исполнители и роли
   переходов видят документ, у каждого перехода есть кто-то, кто его
   выполнит, участник не теряет доступ по ходу процесса, обязательные поля
   кто-то может заполнить, документ кто-то может создать, разделение
   обязанностей выполнимо (`A4`–`A7`, `A11`, `A14`, `A15`).
8. **`make test-b` зелёный.**

### Уровень A — условия, действия переходов, самоназначение, политика (≈ +10–12 ч)

9. **Условия и действия (≈ 3–4 ч)** — `conditions.lint_condition`,
   `effects.lint_effect` по [`docs/spec/05-conditions-effects-policy.md`](docs/spec/05-conditions-effects-policy.md):
   язык условий, синтаксис действий переходов (`effects`) и типы значений
   (`S1.condition`, `S2.effect`, `S2.effect_type`; внимательно — таблица
   `compat` § 5.4.4 и порядок её строк), связи процессов через `fire`
   (`S2.fire_not_system`, `S2.system_unused`). Обе функции вызываются из
   нормализации; место находки передаётся им словарём `where`.
10. **Самоназначение (≈ 5–6 ч)** — может ли участник сам (правом на запись
    или через действие перехода) сделать себя держателем роли (`A8.*`).
    Это самый плотный текст спецификации (§ 5.6.4–5.6.5: кто нажимает,
    распространение до неподвижной точки, помеченные поля). Переносите
    псевдокод почти построчно и проверяйте себя кейсами `pol-a8-*`.
11. **Политика вуза (≈ 2 ч)** — `policy.py`: обязательные ступени, потолки и
    полы прав, обязательное разделение обязанностей, роли «через запись»
    (`I.*`).
12. **`make test-a` зелёный.**

### Что ещё сделать на любом уровне

- `README_SOLUTION.md` в корне (см. [Сдача](#сдача)) — по ходу работы, а не в последний вечер.
- Свои модульные тесты на ключевые функции (обход графа, построение матрицы) —
  эксперт учитывает их в пределах буквы.
- Ролик по сценарию [`docs/video.md`](docs/video.md).

## Критерии оценки

Оценку ставит эксперт по ролику и собственному прогону тестов на вашем
коммите (с исходными `tests/`).

| Оценка | Условие |
|---|---|
| **A** | зелёные уровни C, B и A (`make test-a` — все кейсы прошли) |
| **B** | зелёные уровни C и B (`make test-b`) |
| **C** | зелёный уровень C (`make test-c`) |
| **D** | уровень C пройден частично |
| **не зачтено** | изменены файлы в `tests/` или нет ролика |

- **Минус одна буква**, если результат в ролике не совпадает с прогоном
  эксперта (другой хеш, другие итоговые строки).
- **Качество кода и собственных тестов** учитывается экспертом в пределах
  буквы: читаемость, разумная декомпозиция, отсутствие «подгонки под кейсы»
  (например, ветвления по ключам конкретных тестовых конфигураций), понимание
  своего кода в ролике.
- Прогон автора на закрытом наборе конфигураций на оценку **не** влияет
  (см. [Прозрачность](#прозрачность-что-автор-сделает-с-решениями)).

## Сдача

1. **Репозиторий.** Публичный форк этого репозитория или репозиторий,
   созданный кнопкой «Use this template». Решение — в ветке `main`.
2. **Ссылка и хеш.** Отправьте ссылку на репозиторий и полный хеш сдаваемого
   коммита (`git log -1 --format=%H`) туда, куда укажет преподаватель.
   После отправки хеша коммиты в репозиторий не влияют на оценку.
3. **`README_SOLUTION.md`** в корне репозитория:
   - какой уровень сдаёте и что сделано;
   - ключевые проектные решения (структуры данных, декомпозиция, как
     избегаете каскада находок);
   - где вы разошлись со спецификацией или трактовали её (если такое было);
   - **журнал времени**: дата — сколько часов — что делали;
   - **какие ИИ-инструменты использовались** и для чего (генерация кода,
     объяснение спецификации, отладка, тесты) — или «не использовались»;
   - для реализации не на Python — команды сборки и значение `BPM_IMPL`.
4. **Ролик** не длиннее 7 минут по сценарию [`docs/video.md`](docs/video.md);
   ссылка — в `README_SOLUTION.md` и в сообщении о сдаче.

## Сроки

По общему регламенту семинара наставника:

- представление топика — на сессии (с 25.10.2026);
- выбор топиков однокурсниками — около 5 дней после представления;
- выполнение — 14–16 дней с момента выбора;
- сдача — ссылка, хеш и ролик к сроку, который объявит преподаватель.

Точные даты объявляет преподаватель. Ориентир по нагрузке: уровень C —
≈ 10–12 ч, C + B — ≈ 15–19 ч, все три уровня — ≈ 25–31 ч, то есть около
2 часов в день на весь срок.

## Прозрачность: что автор сделает с решениями

Топик связан с ВКР автора — low-code BPM-движком, ядро которого вы
реализуете. Поэтому честно о том, что произойдёт с вашими решениями:

- **Закрытый прогон.** Кроме приёмочных тестов, автор дополнительно
  прогонит реализации исполнителей и свою (эталонную) на закрытом наборе
  конфигураций, чтобы сравнить, где независимые реализации одной
  спецификации расходятся. **На оценку это не влияет**: оценка определяется только
  открытыми тестами и роликом.
- **Упоминание в ВКР** результатов сравнения возможно **только с согласия
  исполнителя** — в обезличенном виде («реализация 1») или с указанием
  авторства, как вы выберете. Без согласия ваша реализация в тексте ВКР не
  упоминается. Отказ на оценку не влияет.
- Код решения остаётся вашим (лицензию выбираете вы; скелет — MIT).

## Для эксперта: проверка за 5 минут

Нужны git и Python 3.10+. `<URL-решения>` и `<ХЕШ>` — из сдачи.

```bash
# 1. Решение на сданном хеше
git clone <URL-решения> sol && cd sol
git checkout <ХЕШ>

# 2. Восстановить исходные tests/ из репозитория топика (одной командой)
rm -rf tests && git fetch https://github.com/dgornin/bpm-core-topic.git main && git checkout FETCH_HEAD -- tests

# 3. Были ли изменения в tests/ у студента? (пусто — не было)
git diff --stat <ХЕШ> FETCH_HEAD -- tests

# 4. Прогон по уровням
make test-c; make test-b; make test-a
#   без make: python3 tests/run_acceptance.py --level C / B / A
#   не Python: BPM_IMPL="<из README_SOLUTION.md>" make test-a (после сборки)
```

Затем:

1. Сверьте итоговые строки `C: x/y, B: …, A: …` и хеш с роликом
   (несовпадение — минус буква).
2. Если шаг 3 показал отличия в `tests/`, проверьте `CHANGELOG.md`: отличия
   допустимы, только если после форка вышла новая версия кейсов топика
   (тогда засчитывается прогон на восстановленных тестах). Иначе — «не зачтено».
3. Буква — по таблице [критериев](#критерии-оценки); качество кода, тестов
   и защиты в ролике — в пределах буквы.

## FAQ

**Можно ли писать не на Python?**
Да, если соблюдён контракт CLI ([`docs/contract.md`](docs/contract.md)):
те же команды, JSON в stdout, коды выхода. Тесты запускаются с переменной
`BPM_IMPL`, например `BPM_IMPL="./target/release/bpmcore" make test-a`.
Скелет на Python тогда можно удалить; `tests/` не трогайте. Опишите сборку
в `README_SOLUTION.md` — эксперт должен собрать решение по инструкции за
пару минут.

**Можно ли пользоваться ИИ-ассистентами (Copilot, ChatGPT, Claude…)?**
Да. Укажите в `README_SOLUTION.md`, какие и для чего. Будьте готовы, что в
ролике нужно объяснить проектное решение и трудность своими словами — это
и есть защита: если по ролику видно, что вы не понимаете свой код, эксперт
учтёт это в пределах буквы.

**Можно ли менять скелет (`cli.py`, `validate.py`, структуру модулей)?**
Да, всё, кроме `tests/`. Контракт CLI должен остаться прежним.

**Тест падает, а по-моему спецификация говорит другое. Что делать?**
Ожидаемые ответы сгенерированы эталонной реализацией, а не написаны руками,
поэтому кейс — источник истины. Если текст спецификации неясен или
противоречит кейсу, откройте **issue в репозитории топика**: в заголовке —
имя кейса или раздел спецификации. Ответы и исправления публикуются там же и
в `CHANGELOG.md`.

**Почему кейс ожидает два-три кода, а не один?**
Одна поломка часто нарушает несколько свойств сразу (например, тупиковый
шаг — это и `S3.dead_end`, и `S5.no_end`). Нужно выдать все ожидаемые коды;
лишние коды тестами не штрафуются, но это ложные срабатывания.

**Нужен ли Odoo, база данных, сеть?**
Нет. Ядро работает с одним JSON-файлом. Упоминания платформы в
спецификации (например, `create_uid`, `res.users`) — это только имена,
описанные в спецификации и снимке платформы.
